¿Qué son Git y GitHub?

Aunque casi siempre se nombran juntos, son dos cosas distintas que se complementan:

  • Git es un programa que instalas en tu computadora. Guarda el historial de tu proyecto en “puntos de guardado” llamados commits, para que puedas ver qué cambió, volver atrás y probar ideas sin miedo a romper nada. Funciona sin internet.
  • GitHub es un sitio web que guarda en internet una copia de tus proyectos de Git. Sirve como respaldo, para compartir tu código y para trabajar con otras personas (con pull requests, issues y más).

Una forma fácil de imaginarlo

Piensa en un videojuego: Git son las partidas guardadas de tu consola (puedes volver a cualquiera de ellas) y GitHub es subir esas partidas a la nube para no perderlas y compartirlas con otras personas.

Por qué te sirve, sobre todo si programas con IA

  • Una IA puede modificar diez archivos de un solo golpe. Con Git ves exactamente qué cambió y puedes deshacerlo.
  • Puedes probar una idea en una rama aparte y borrarla si no sale bien.
  • Tu código queda respaldado en GitHub aunque se dañe tu computadora.
  • En equipo, cada persona avanza por su lado y después los cambios se juntan de forma ordenada y revisada.

Qué vas a encontrar en esta guía

  1. Primero lo básico: instalar Git, el vocabulario y los comandos del día a día.
  2. Después, tres casos completos: trabajar solo con tu IA, trabajar en equipo y revisar los cambios de otras personas.
  3. Al final: deshacer errores, comandos avanzados, las herramientas de GitHub y una referencia rápida con los errores más comunes.
No necesitas memorizar nada

Con unos pocos comandos haces el 90 % del trabajo (status, add, commit, push y pull). El resto lo consultas aquí cuando lo necesites. Ten en cuenta que los mensajes de Git aparecen en inglés; en esta guía te explico los más comunes.

Instalar y configurar Git

Esto se hace una sola vez por computadora y tarda unos minutos.

1. Revisa si ya lo tienes

Abre una terminal (PowerShell o CMD) y escribe:

git --version

Si responde algo como git version 2.47.1.windows.1, ya lo tienes. Si dice que no reconoce el comando, sigue con el paso 2.

2. Instálalo en Windows

La forma más sencilla es con winget, que viene con Windows 11 y con las versiones recientes de Windows 10:

winget install --id Git.Git -e --source winget

También puedes descargar el instalador de Git for Windows desde git-scm.com y dejar las opciones que trae por defecto. Al terminar, cierra y vuelve a abrir la terminal para que reconozca el comando.

Si el instalador pregunta por el editor

Elige uno que conozcas (Notepad o VS Code) en lugar de Vim. Vim es muy potente, pero desconcierta a quien está empezando.

3. Dile a Git quién eres

Cada commit lleva tu nombre y tu correo. Configúralos una sola vez (cambia los datos por los tuyos):

git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo@ejemplo.com"

Usa el mismo correo de tu cuenta de GitHub para que tus commits se asocien a tu perfil. Si prefieres no mostrar tu correo real, GitHub te da uno privado que termina en @users.noreply.github.com (lo ves en Settings → Emails).

4. Ajustes recomendados

git config --global init.defaultBranch main
git config --global push.autoSetupRemote true
git config --global pull.rebase false
AjustePara qué sirve
init.defaultBranch mainLos repositorios nuevos empiezan con la rama main, que es el nombre que usa GitHub.
push.autoSetupRemote trueLa primera vez que subes una rama nueva, Git la conecta solo con GitHub y no tienes que escribir -u origin nombre. Requiere Git 2.37 o más nuevo.
pull.rebase falseHace que git pull junte los cambios con una fusión (merge) y evita un aviso que confunde al principio.

Para revisar cómo quedó tu configuración:

git config --global --list

5. Conecta tu computadora con GitHub

  1. Crea tu cuenta en github.com si aún no la tienes.
  2. Activa la verificación en dos pasos (Settings → Password and authentication). Protege tu cuenta y GitHub la exige a quienes publican código.
  3. Elige cómo se identificará tu computadora: HTTPS (lo más fácil) o SSH.

Opción A (recomendada): HTTPS

Git for Windows incluye el Git Credential Manager. La primera vez que hagas git push o git clone de un repositorio privado se abre una ventana del navegador: inicias sesión en GitHub, autorizas y listo. No vuelve a pedirte nada.

La contraseña de tu cuenta ya no sirve en la consola

Si Git te pide usuario y contraseña en la terminal, recuerda que GitHub dejó de aceptar la contraseña de la cuenta para Git en 2021. Usa el inicio de sesión del navegador o un token de acceso personal.

Opción B: SSH (se configura una vez y no pide nada más)

Primero creas un par de claves y copias la pública (la que termina en .pub):

ssh-keygen -t ed25519 -C "tu-correo@ejemplo.com"
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard

Pulsa Enter para aceptar la ubicación por defecto (la contraseña de la clave es opcional). Luego, en GitHub, ve a Settings → SSH and GPG keys → New SSH key, pega la clave y guárdala. Para probar:

ssh -T git@github.com

Si ves Hi tu-usuario! You've successfully authenticated, funcionó. Desde ahora clona con las direcciones que empiezan con git@github.com:.

Nunca compartas tu clave privada ni tus tokens

El archivo id_ed25519 (sin .pub) y los tokens de acceso son como tu contraseña. No los pegues en chats, no los subas a un repositorio y no se los des a nadie.

Dos sorpresas que son normales

  • “LF will be replaced by CRLF”: es un aviso habitual en Windows sobre los saltos de línea. No es un error y no tienes que hacer nada.
  • Se abrió una pantalla rara (Vim): pasa cuando haces git commit sin -m. Para salir sin guardar pulsa Esc, escribe :q! y pulsa Enter. Para guardar y salir, escribe :wq.

¿Para qué existe el área de preparación?

Para que tú decidas qué entra en cada commit. Si cambiaste cinco archivos pero solo tres tienen que ver con la misma tarea, preparas esos tres, haces un commit, y luego preparas los otros dos en un commit aparte. Así el historial queda ordenado y fácil de leer.

Comandos básicos, uno por uno

Estos nueve comandos cubren casi todo lo que harás cada día. De cada uno verás para qué sirve, cómo se escribe y cuándo usarlo.

El ciclo del día a día

Cuando ya tienes un repositorio, casi siempre repites estos pasos:

git status
git add .
git commit -m "Describe lo que cambiaste"
git push
  1. Editas tus archivos (tú o tu IA).
  2. git status: miras qué cambió.
  3. git add .: preparas esos cambios.
  4. git commit -m "...": los guardas en el historial.
  5. git push: los subes a GitHub.

git init: crear un repositorio

Convierte la carpeta donde estás en un repositorio de Git (crea la carpeta oculta .git). Se usa una sola vez por proyecto.

mkdir mi-proyecto
cd mi-proyecto
git init

git clone: descargar un repositorio

Descarga un repositorio completo (archivos e historial) y lo deja conectado a GitHub con el nombre origin. La dirección la copias del botón verde Code de la página del repositorio.

git clone https://github.com/usuario/repositorio.git
git clone https://github.com/usuario/repositorio.git mi-carpeta
cd repositorio

El segundo ejemplo guarda el proyecto en una carpeta con el nombre que tú elijas. Después de clonar, entra a la carpeta con cd.

git status: ver qué está pasando

Es el comando que más vas a usar. Te dice en qué rama estás, qué archivos cambiaron y cuáles están preparados. Úsalo antes de cada add y cada commit.

git status
git status -s
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   index.html

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   estilos.css

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        notas.txt

Se lee en tres bloques:

  • Changes to be committed: ya están preparados (con git add) y entrarán en el próximo commit.
  • Changes not staged for commit: los modificaste, pero aún no los preparaste.
  • Untracked files: archivos nuevos que Git todavía no conoce.

Con -s obtienes una versión corta. La primera columna es lo preparado y la segunda lo que falta preparar:

M  index.html
 M estilos.css
?? notas.txt

git add: preparar cambios

Marca qué cambios entrarán en el próximo commit. No sube nada a GitHub: solo los deja en la “sala de espera”.

git add index.html      # un archivo
git add carpeta/        # una carpeta completa
git add .               # todo lo que cambió desde donde estás
git add -p              # eliges trozo por trozo qué entra
Mira antes de usar git add .

Prepara todo, incluidos archivos nuevos. Haz git status primero para asegurarte de no incluir contraseñas, archivos pesados o cosas temporales.

git commit: guardar en el historial

Crea el punto de guardado con lo que está preparado.

git commit -m "Agrega el formulario de contacto"
git commit -am "Corrige el color del botón"
  • -m "mensaje" escribe el mensaje directamente. Sin -m se abre un editor.
  • -a prepara automáticamente los archivos que ya estaban en Git y que modificaste (no incluye archivos nuevos). Es un atajo para ahorrarte el git add.
  • El commit se queda en tu computadora hasta que hagas git push.
  • Un buen mensaje explica qué cambiaste y por qué. Mira la sección de buenas prácticas.

git push: subir a GitHub

Envía tus commits al repositorio remoto.

git push
git push -u origin main

El segundo comando se usa la primera vez que subes una rama: -u conecta tu rama local con la de GitHub, y a partir de ahí basta con git push. Si activaste push.autoSetupRemote en la configuración, tampoco lo necesitas para ramas nuevas.

Si GitHub rechaza el push (rejected), casi siempre es porque tiene commits que tú no tienes. Haz primero un git pull.

git pull: traer las novedades

Descarga los commits nuevos de GitHub y los mezcla con tu rama. Hazlo al empezar a trabajar, sobre todo si trabajas en equipo o desde varias computadoras.

git pull
git fetch

git pull es en realidad git fetch (traer) más git merge (mezclar). Si solo quieres mirar qué hay de nuevo sin tocar tus archivos, usa git fetch.

git log: ver el historial

Lista los commits, del más reciente al más antiguo.

git log
git log --oneline
git log --oneline --graph --decorate --all
git log -5

Así se ve git log --oneline en este mismo repositorio:

383f976 (HEAD -> main, origin/main) Actualiza el README con el estado y como agregar contenido
dbb368e Agrega el inicio y la pagina de cada tema
0f15ce5 Agrega estilos, buscador y comportamiento de la pagina
e9312d3 Estructura inicial del repositorio
  • Si el historial es largo, Git lo muestra por páginas: usa Espacio para avanzar y q para salir.
  • Opciones útiles: --stat (qué archivos tocó cada commit), -p (los cambios línea por línea), --author="nombre", --since="1 week ago" y --grep="palabra".

git diff: ver qué cambió

Muestra las diferencias línea por línea.

git diff                  # cambios que aún no preparaste
git diff --staged         # cambios preparados (lo que entrará en el commit)
git diff main..mi-rama    # diferencias entre dos ramas
git diff --stat           # resumen: archivos y cantidad de líneas
diff --git a/estilos.css b/estilos.css
--- a/estilos.css
+++ b/estilos.css
@@ -10,3 +10,3 @@
 .boton {
-  color: red;
+  color: blue;
 }

Las líneas con - son las que se quitaron y las que tienen + son las que se agregaron. Las demás son contexto. Como el historial, si es largo se sale con q.

Un hábito que te ahorra sustos

Antes de cada commit, mira git status y git diff --staged. Son dos segundos y evitan subir cosas por error. Ten en cuenta que git diff no muestra los archivos nuevos sin seguimiento: esos los ves con git status.

Crear un repositorio

Hay dos caminos. Los dos terminan igual: una carpeta en tu computadora conectada con un repositorio en GitHub.

CaminoCuándo convieneResumen
A. Crearlo en GitHub y clonarloProyecto nuevo. Es el más fácil para empezar.Crear en github.com, luego git clone.
B. Empezar en tu PC y subirloYa tienes una carpeta con código (por ejemplo, algo que hiciste con tu IA).git init, commit, crear repo vacío, conectar y git push.

Camino A: crearlo en GitHub y clonarlo

  1. En github.com pulsa el botón + (arriba a la derecha) y elige New repository.
  2. Ponle un nombre sin espacios (usa guiones, por ejemplo mi-proyecto) y una descripción corta.
  3. Elige Public (cualquiera puede verlo) o Private (solo tú y quien invites).
  4. Es útil marcar Add a README file, elegir una plantilla de .gitignore para tu lenguaje y, si vas a compartir el código, una licencia.
  5. Pulsa Create repository, copia la dirección del botón verde Code y clónalo:
git clone https://github.com/tu-usuario/mi-proyecto.git
cd mi-proyecto

Ya puedes trabajar: crea archivos, haz git add, git commit y git push.

Camino B: empezar en tu PC y subirlo

Es el camino cuando ya tienes una carpeta con código.

  1. Crea el repositorio vacío en GitHub, igual que arriba pero sin marcar README, .gitignore ni licencia. Si los agregas, el repositorio remoto ya tendrá un commit y tendrás que mezclar historiales.
  2. En tu computadora, dentro de la carpeta del proyecto, ejecuta:
git init
git add .
git commit -m "Primer commit"
git branch -M main
git remote add origin https://github.com/tu-usuario/mi-proyecto.git
git push -u origin main
  • git init crea el repositorio local.
  • git add . y git commit guardan el primer punto del historial.
  • git branch -M main se asegura de que la rama se llame main.
  • git remote add origin ... conecta tu carpeta con el repositorio de GitHub.
  • git push -u origin main sube todo y deja la rama conectada.
Crea el .gitignore antes del primer git add .

Así no subes por accidente carpetas pesadas (como node_modules) ni archivos con contraseñas. Más detalles en la sección de buenas prácticas.

Con GitHub CLI (opcional)

Si tienes instalada la herramienta gh (la explico en la sección de GitHub más allá del código), puedes crear el repositorio en GitHub y subir tu carpeta en un solo paso, siempre que ya tengas al menos un commit:

gh repo create mi-proyecto --private --source=. --remote=origin --push

Cambia --private por --public si quieres que cualquiera pueda verlo.

Reglas para mantener todo ordenado

  • Un repositorio por proyecto. No mezcles proyectos distintos en el mismo.
  • Nombres en minúsculas y con guiones: guia-programadores.
  • Escribe un README desde el primer día, aunque sea corto.
  • No crees un repositorio dentro de otro (una carpeta con .git dentro de otra que también la tiene).
  • Si tienes OneDrive o Dropbox sincronizando tus carpetas, guarda los repositorios en una carpeta fuera de ellas (por ejemplo C:\proyectos). Sincronizar la carpeta .git mientras Git la modifica puede causar errores raros.

Caso 1: trabajar solo con tu IA

Eres tú y una IA (por ejemplo, la de Cursor) editando el mismo proyecto. Nadie más revisa el código, así que Git es tu red de seguridad: te deja probar sin miedo, ver exactamente qué cambió la IA y volver atrás cuando algo sale mal.

Qué necesitas

  • Un repositorio (Camino A o B de la sección “Crear un repositorio”). Hazlo privado si el proyecto tiene datos personales o claves.
  • Un archivo .gitignore para no subir carpetas pesadas ni contraseñas.
  • Que la rama main siempre tenga una versión que funcione.
La regla de oro

Haz un commit antes de pedirle algo grande a la IA. Así siempre tienes un punto al que volver, pase lo que pase.

El flujo, paso a paso

  1. Empieza limpio. Ejecuta git status. Si hay cambios sueltos, guárdalos primero con un commit.
  2. Crea una rama corta para la tarea (opcional, pero muy recomendable). Si la tarea sale mal, borras la rama y main queda intacto.
  3. Pídele a la IA una tarea pequeña y concreta. Mejor “agrega el botón de borrar” que “termina toda la aplicación”.
  4. Revisa lo que cambió con git status y git diff, o con el panel de control de código fuente de tu editor.
  5. Pruébalo. Ejecuta el programa y comprueba que hace lo que pediste y que no rompió lo anterior.
  6. Si está bien, guárdalo con git add y git commit. Si no, descarta los cambios (mira la tabla de más abajo).
  7. Repite desde el paso 3 con la siguiente tarea.
  8. Cuando la rama esté lista, fusiónala con main y sube todo a GitHub.
git switch main
git pull
git switch -c feature/menu-principal
# ...aquí trabajas con la IA...
git status
git diff
git add .
git commit -m "Agrega el menú principal"
git switch main
git merge feature/menu-principal
git push
git branch -d feature/menu-principal

Si prefieres no usar ramas

En proyectos pequeños puedes trabajar directamente en main. La regla es la misma: un commit antes de cada tarea de la IA y otro cuando compruebes que quedó bien. Las ramas dan más tranquilidad cuando la tarea es grande o es un experimento.

Qué mirar al revisar lo que hizo la IA

  • ¿Tocó solo los archivos que esperabas? Compruébalo con git status y git diff --stat.
  • ¿Borró o reescribió código que ya funcionaba?
  • ¿Agregó librerías, archivos o configuraciones que no pediste?
  • ¿Dejó contraseñas, claves de API o datos personales dentro del código?
  • ¿Funciona de verdad? Ejecútalo antes de guardar.
git diff --stat

Muestra un resumen con los archivos modificados y cuántas líneas cambiaron en cada uno. Es una forma rápida de detectar si la IA tocó más de lo que debía.

Si la IA rompió algo: cómo volver atrás

SituaciónQué hacer
Aún no hiciste commit y quieres descartar todo lo que cambiógit restore . y, si creó archivos nuevos, git clean -fd. Antes usa git clean -n para ver qué borraría.
Descartar solo un archivogit restore ruta/archivo
Ya hiciste commit y quieres deshacerlo, conservando los cambios en tus archivosgit reset --soft HEAD~1
Quieres deshacer un commit dejando constancia (también si ya hiciste push)git revert HEAD
Volver a un commit anterior y tirar todo lo posteriorgit reset --hard abc1234 (peligroso: solo si aún no hiciste push)
La tarea salió mal en una ramagit switch main y luego git branch -D feature/nombre

Cada una de estas opciones se explica con calma en Deshacer cosas sin miedo.

Cuidado con los comandos que borran trabajo

git restore ., git clean -fd y git reset --hard eliminan cambios sin avisar y no se pueden recuperar. Si tu IA puede ejecutar comandos en la terminal, haz que te pida confirmación antes de usarlos y nunca le permitas git push --force.

Usar Git desde tu editor

En Cursor (y en VS Code) abre el panel de Control de código fuente con Ctrl + Shift + G, o con el icono de las ramas en la barra lateral. Desde ahí puedes:

  • Ver la lista de archivos cambiados y abrir cada uno para ver la diferencia.
  • Prepararlos con el signo +, escribir el mensaje y pulsar Commit.
  • Hacer Pull y Push desde el menú ⋯.
  • Ver la rama actual abajo a la izquierda. Si haces clic ahí, puedes cambiar de rama o crear una nueva.

Algunos editores pueden sugerirte el mensaje del commit con IA. Está bien usarlo, pero léelo siempre: tiene que decir qué cambió y por qué.

Respáldalo con git push

Un commit solo existe en tu computadora hasta que lo subes. Haz git push al terminar cada sesión de trabajo y tu proyecto quedará a salvo en GitHub.

Dos frases que ayudan a que la IA no se pase de lista

“Antes de cambiar nada, dime qué archivos vas a modificar y por qué.” y “Haz solo este cambio y no toques otros archivos.” Así los cambios son pequeños y fáciles de revisar con git diff.

Ramas y fusiones

Una rama es una línea de trabajo independiente. Cuando la creas, parte de donde estás, y todo lo que hagas en ella no afecta a las demás. Cuando termina y funciona, la fusionas con main.

          D --- E        mi-rama
         /       \
A --- B --- C --- F      main  (F es el commit de fusión)

Crear, ver y cambiar de rama

git branch                       # lista las ramas locales (la actual lleva *)
git branch -a                    # incluye también las del remoto
git switch -c feature/login      # crea la rama y se cambia a ella
git switch main                  # cambia a otra rama
git switch -                     # vuelve a la rama anterior
ComandoQué hace
git branch nombreCrea la rama pero te deja donde estás.
git branch -d nombreBorra una rama que ya fue fusionada.
git branch -D nombreFuerza el borrado, aunque tenga commits sin fusionar (se pierden).

git branch -vvMuestra de qué rama remota depende cada rama.
git checkout nombreLa forma antigua de git switch. Sigue funcionando y la verás en muchos tutoriales.

Fusionar una rama (merge)

Te paras en la rama que recibe los cambios (normalmente main) y fusionas la otra:

git switch main
git merge feature/login

Pueden pasar dos cosas:

  • Avance rápido (fast-forward): si main no cambió desde que creaste la rama, Git solo mueve el puntero hacia adelante. No se crea ningún commit extra y el historial queda en línea recta.
  • Commit de fusión: si main también avanzó, Git crea un commit especial que junta las dos líneas (la F del dibujo). Si las dos ramas cambiaron las mismas líneas, aparece un conflicto que resuelves tú.
git merge --no-ff feature/login     # siempre crea commit de fusión
git merge --squash feature/login    # junta todos sus commits en uno (luego haces tú el commit)
git merge --abort                   # cancela una fusión que se complicó

Subir y traer ramas de GitHub

git push -u origin feature/login
git fetch
git switch feature/login

El primero publica tu rama en GitHub (si activaste push.autoSetupRemote, te basta con git push). Los otros dos sirven para trabajar con una rama que alguien más subió: git fetch trae la información y git switch crea tu copia local, ya conectada.

Borrar ramas cuando terminas

git branch -d feature/login                # borra la rama en tu computadora
git push origin --delete feature/login     # la borra también en GitHub
git fetch --prune                          # limpia las referencias a ramas que ya no existen en GitHub

Tras fusionar un pull request, GitHub muestra un botón Delete branch que hace el segundo paso por ti.

Cambiar de rama con cambios sin guardar

Si tus cambios no chocan con la otra rama, Git te deja cambiar y los lleva contigo. Si chocan, avisa con Your local changes ... would be overwritten y no cambia nada. En ese caso haz un commit, o guárdalos temporalmente con git stash (lo verás en Deshacer cosas sin miedo).

Una forma sencilla de usar ramas

  1. main siempre contiene una versión que funciona.
  2. Cada tarea nueva va en una rama que sale de main.
  3. Haces commits pequeños en esa rama.
  4. Cuando está lista, la fusionas (tú solo con merge, o en equipo con un pull request).
  5. Borras la rama y empiezas la siguiente.

  1. Elige o crea un issue: la tarea que vas a hacer (más abajo).
  2. Actualiza tu main para partir de lo último.
  3. Crea tu rama con un nombre que describa la tarea.
  4. Trabaja con commits pequeños y claros.

  • Título claro: “Agrega filtro de búsqueda por categoría”.

Issues: las tareas del equipo

Un issue es una tarea, un error o una idea, con su propia conversación. Se crean en la pestaña Issues → New issue.

  • Ponle un título claro y explica qué hay que hacer o cómo reproducir el error.

Mantén tu rama al día

Mientras trabajas, main puede avanzar con el trabajo de otras personas. Trae esos cambios a tu rama de vez en cuando, sobre todo antes de abrir el pull request: si hay conflictos, los verás pronto, cuando todavía son pequeños.

git switch feature/123-filtro-de-busqueda

git merge origin/main

En la página del pull request, GitHub también ofrece un botón Update branch que hace lo mismo. Hay otra opción, rebase, que verás en Comandos avanzados.

Colaborar con un fork

  1. En la página del repositorio original pulsa Fork (arriba a la derecha). GitHub crea una copia a tu nombre.

git push

En la web de tu fork hay un botón Sync fork que hace lo mismo.

El botón verde de un pull request tiene tres modos. Tu equipo debería elegir uno y mantenerlo.

Reglas de equipo que evitan problemas

  • Nadie sube directo a main. Protégela en Settings → Branches (o Settings → Rules → Rulesets) con las reglas Require a pull request before merging, Require approvals y Block force pushes.
  • Haz git pull al empezar cada jornada.
  • Una persona por rama. Si dos van a trabajar en la misma, avísense antes.
  • Commits pequeños y mensajes claros.

Caso 3: revisar los cambios de otros

Revisar es leer los cambios que alguien propone antes de que entren a main. Puedes hacerlo en GitHub (lo más cómodo) y en tu terminal, cuando necesitas probar el código o comparar a fondo.

Revisar un pull request en GitHub

  1. Abre el pull request desde la pestaña Pull requests y lee primero el título y la descripción: ¿qué se quiere lograr?
  2. En Conversation mira los comentarios, los issues enlazados y, al final, el estado de los checks (pruebas automáticas).
  3. Ve a Files changed. Ahí cada archivo muestra las líneas agregadas (verde) y las quitadas (rojo).
  4. Marca cada archivo como Viewed para no perder la cuenta.
  5. Para comentar una línea, pasa el mouse por encima y pulsa el + azul (arrastra para elegir varias líneas). Con Add a suggestion puedes proponer el cambio exacto y la otra persona lo acepta con un clic.
  6. Al terminar, pulsa Review changes, escribe un resumen y elige una opción.

Qué revisar

  • ¿Hace lo que dice la descripción y resuelve el issue?
  • ¿Se entiende el código? Nombres claros, sin duplicados y sin código comentado que sobre.
  • ¿Maneja los casos raros? Listas vacías, valores vacíos, errores.
  • ¿Puede romper algo que ya funcionaba? ¿Hay pruebas nuevas o actualizadas?
  • ¿Hay contraseñas, claves o datos personales dentro del código?
  • ¿Los archivos tocados tienen sentido? Atento a archivos basura como node_modules o .env.
  • ¿Es demasiado grande? Si cuesta leerlo, pide dividirlo en pull requests más pequeños.
Si el código lo escribió una IA

Revísalo como el de una persona nueva en el equipo. Suele funcionar en el caso feliz y fallar en los bordes. Puedes pedirle a otra IA que resuma el pull request o busque errores, pero úsala como segunda opinión: la decisión de aprobar es tuya.

Resolver conflictos

Un conflicto aparece cuando dos ramas cambiaron las mismas líneas de un archivo (o una borró un archivo que la otra modificó) y Git no puede decidir cuál versión conservar. No es un error ni algo grave: es Git pidiéndote que decidas tú.

Cuándo ocurre

  • Al hacer git merge o git pull.
  • Al hacer git rebase o git cherry-pick.
  • Al recuperar cambios con git stash pop.
  • En un pull request, cuando main avanzó sobre las mismas líneas que tocaste.

Cómo se ve

Al fusionar, Git te avisa y se detiene a mitad de camino:

Auto-merging estilos.css
CONFLICT (content): Merge conflict in estilos.css
Automatic merge failed; fix conflicts and then commit the result.

Con git status ves qué archivos hay que arreglar:

You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   estilos.css

both modified significa que las dos ramas cambiaron ese archivo.

Leer los marcadores

Git escribe dentro del archivo las dos versiones, separadas por unos marcadores:

.boton {
<<<<<<< HEAD
  color: blue;
=======
  color: green;
>>>>>>> feature/colores
}
  • Entre <<<<<<< HEAD y ======= está tu versión, la de la rama donde estás parado.
  • Entre ======= y >>>>>>> feature/colores está la versión de la otra rama.
  • Tu trabajo es dejar una versión final (una de las dos o una mezcla) y borrar las tres líneas de marcadores.
.boton {
  color: green;
}

Resolverlo paso a paso

  1. Ejecuta git status para ver qué archivos están en conflicto.
  2. Abre cada uno y busca los marcadores <<<<<<< (con Ctrl + F).
  3. Decide qué se queda: tu versión, la otra, o una mezcla. Edita el texto y borra las líneas de marcadores.
  4. Prueba que el proyecto funciona.
  5. Marca el archivo como resuelto con git add.
  6. Termina la fusión con git commit.
git status
# ...editas el archivo y borras los marcadores...
git add estilos.css
git commit --no-edit

--no-edit usa el mensaje de fusión que Git ya preparó. Sin esa opción se abre el editor de texto con el mismo mensaje.

Resolverlo desde el editor

Cursor y VS Code detectan los marcadores y muestran, sobre cada conflicto, estos botones:

  • Accept Current Change: te quedas con tu versión.
  • Accept Incoming Change: te quedas con la de la otra rama.
  • Accept Both Changes: conservas las dos, una debajo de otra.
  • Compare Changes: las ves lado a lado.

Para conflictos grandes, el botón Resolve in Merge Editor abre una vista de tres paneles (tu versión, la otra y el resultado). Cuando termines, guarda el archivo, haz git add y git commit.

Si dejas que una IA resuelva el conflicto

Revisa el resultado. Debe conservar lo importante de los dos lados, no solo de uno. Pídele que explique qué decidió y por qué, y prueba el programa antes de hacer el commit.

Resolverlo en GitHub

Si un pull request dice This branch has conflicts that must be resolved, pulsa Resolve conflicts. La página muestra los mismos marcadores: edítalos, pulsa Mark as resolved y luego Commit merge. Es cómodo para conflictos pequeños; para los complicados, es mejor hacerlo en tu computadora, donde puedes probar el código.

git rebase --abort

Cómo evitar conflictos

  • Haz git pull a menudo y mantén tu rama al día con main.
  • Usa ramas cortas y pull requests pequeños.
  • Evita que dos personas editen el mismo archivo a la vez sin avisarse.
  • No mezcles un reformateo de archivos enteros con cambios de lógica.
Un conflicto no es culpa de nadie

Respira, lee los dos lados y, si no entiendes el cambio de la otra persona, pregúntale antes de decidir cuál se queda.

Casi todo en Git se puede deshacer si antes lo guardaste en un commit. Lo único que se pierde para siempre son los cambios que nunca se guardaron. Esta sección está organizada por pregunta: ¿en qué punto estoy y qué quiero recuperar?

git restore .                              # descarta los cambios de todos los archivos

git restore archivo descarta los cambios sin avisar y no se pueden recuperar. Si tienes dudas, usa antes git stash: guarda tus cambios en un cajón y puedes volver a sacarlos.

El primero cambia el mensaje. Los otros dos agregan un archivo olvidado al último commit sin tocar su mensaje. Úsalo solo si aún no hiciste push: --amend crea un commit nuevo (con otra identificación) y reemplaza al anterior.

git reset: mover la rama hacia atrás

Mueve tu rama a un commit anterior. La diferencia entre sus tres modos está en qué pasa con tus cambios:

ModoLo preparado (add)Tus archivosPara qué sirve
--softSe queda preparado.No cambian.Rehacer el commit o juntar varios en uno.
--mixed (el predeterminado)Se vacía.No cambian.Deshacer el commit y elegir de nuevo qué preparar.
--hardSe vacía.Se sobrescriben: pierdes los cambios.Tirar todo y volver a ese punto exacto.
 
git reset --soft HEAD~1         # deshace el último commit; los cambios siguen preparados
git reset HEAD~1                # deshace el último commit; los cambios quedan sin preparar
git reset --hard HEAD~1         # deshace el último commit y borra sus cambios
git reset --hard abc1234        # vuelve exactamente a ese commit
git reset --hard origin/main    # deja tu rama igual que la de GitHub (descarta lo local)

HEAD~1 es el commit anterior al actual, HEAD~2 el anterior a ese, y así sucesivamente.

reset reescribe el historial

Úsalo solo con commits que no hayas subido. Si ya hiciste push y otras personas pueden haber descargado esos commits, usa git revert.

git revert: deshacer sin reescribir

En lugar de borrar un commit, crea uno nuevo que hace exactamente lo contrario. El historial queda intacto, por eso es la opción segura cuando ya compartiste los cambios.

git revert abc1234     # deshace ese commit
git revert HEAD        # deshace el último commit

git stash: guardar cambios en un cajón

Guarda tus cambios sin hacer commit y deja el directorio limpio. Es útil cuando tienes algo a medias y necesitas cambiar de rama, hacer git pull o probar otra cosa.

git stash                            # guarda los cambios de archivos que Git ya conoce
git stash -u                         # guarda también los archivos nuevos
git stash push -m "menu a medias"    # guarda con un nombre
git stash list                       # muestra lo que hay en el cajón
git stash pop                        # recupera lo último y lo saca del cajón
git stash apply                      # lo recupera, pero lo deja en el cajón
git stash drop                       # borra lo último que guardaste
stash@{0}: On main: menu a medias
stash@{1}: WIP on feature/login: 3f2a1b0 Agrega formulario

Para recuperar uno que no es el último usa su nombre, por ejemplo git stash pop stash@{1}.

git reflog: la red de seguridad final

Git anota cada movimiento de tu HEAD (commits, cambios de rama, resets, rebases) durante unos 90 días. Si crees que perdiste commits, por ejemplo después de un reset --hard o de borrar una rama, casi siempre siguen ahí.

git reflog
a1b2c3d HEAD@{0}: reset: moving to HEAD~2
9f8e7d6 HEAD@{1}: commit: Agrega el carrito
5c4b3a2 HEAD@{2}: commit: Agrega el menu

Aquí el reset “borró” dos commits, pero 9f8e7d6 sigue existiendo. Lo más seguro es crear una rama en ese punto para revisarlo:

git switch -c rescate 9f8e7d6

El reflog solo recuerda lo que llegó a estar en un commit. Los cambios que nunca se guardaron (ni con commit ni con stash) no se pueden recuperar.

Comandos avanzados

Estos comandos no los necesitas el primer día. Aprende cada uno cuando aparezca el problema que resuelve.

git rebase: poner tu rama al día sin commit de fusión

rebase vuelve a aplicar tus commits encima de otra base, como si hubieras empezado tu rama más tarde. El resultado es un historial en línea recta, sin commits de fusión.

Antes:
      D --- E          feature
     /
A - B - C - F          main

Después de git rebase main (estando en feature):
                D' --- E'   feature
               /
A - B - C - F               main

D' y E' son copias de D y E con otra identificación: por eso se dice que el rebase reescribe el historial.

git switch feature/login
git rebase main                 # reaplica tus commits encima de main
git rebase --continue           # sigue, después de resolver un conflicto
git rebase --abort              # cancela y vuelve a como estabas

Rebase interactivo: ordenar tus commits

Antes de abrir un pull request puedes limpiar tus últimos commits:

git rebase -i HEAD~3

Se abre un editor con la lista de los últimos tres commits. Cambias la palabra del inicio de cada línea según lo que quieras hacer:

pick 1a2b3c4 Agrega el menu
fixup 5d6e7f8 Corrige un error de tipeo
pick 9a8b7c6 Agrega el carrito
PalabraQué hace
pickUsa el commit tal cual.
rewordUsa el commit, pero te deja cambiar el mensaje.
squashLo junta con el commit anterior y combina los mensajes.
fixupLo junta con el commit anterior y descarta su mensaje.
dropElimina el commit.
editSe detiene en ese commit para que lo modifiques.

En el ejemplo, el segundo commit se une al primero y se descarta su mensaje. También puedes cambiar el orden de las líneas para reordenar los commits.

La regla de oro del rebase

No hagas rebase de commits que ya compartiste (main o ramas que usan otras personas). El rebase crea commits nuevos, y quienes tengan los viejos tendrán problemas para reconciliarse. En ramas tuyas que no usa nadie más, es seguro.

git push --force-with-lease: forzar con seguridad

Después de un rebase o un --amend en una rama que ya habías subido, GitHub rechaza el push normal porque el historial cambió. Para sobrescribirla:

git push --force-with-lease

Sobrescribe la rama de GitHub solo si nadie más subió cambios desde la última vez que la viste. Es mucho más seguro que --force, que pisa todo sin preguntar. Y nunca fuerces main.

git cherry-pick: copiar un commit

Copia un commit concreto de otra rama a la rama donde estás. Es útil, por ejemplo, para llevar un arreglo urgente a otra rama sin fusionar todo lo demás.

git cherry-pick abc1234               # copia ese commit a la rama actual
git cherry-pick abc1234 def5678       # copia varios
git cherry-pick -x abc1234            # anota en el mensaje de dónde viene
git cherry-pick --continue            # sigue, después de resolver un conflicto
git cherry-pick --abort               # cancela

El commit copiado tiene otra identificación que el original, porque es un commit nuevo.

Etiquetas (tag): marcar versiones

Una etiqueta pone un nombre fijo a un commit, normalmente para marcar una versión publicada.

git tag v1.0.0                              # etiqueta ligera en el commit actual
git tag -a v1.0.0 -m "Primera versión"      # etiqueta anotada (la recomendada)
git tag -a v0.9.0 abc1234 -m "Beta"         # etiqueta un commit anterior
git tag                                     # lista las etiquetas
git show v1.0.0                             # muestra los detalles
git push origin v1.0.0                      # sube una etiqueta
git push origin --tags                      # sube todas
git tag -d v1.0.0                           # la borra en tu computadora
git push origin --delete v1.0.0             # la borra en GitHub

Las versiones suelen seguir el esquema MAYOR.MENOR.PARCHE (por ejemplo, v2.4.1): sube MAYOR si hay cambios que rompen la compatibilidad, MENOR si agregas funciones compatibles y PARCHE si solo corriges errores. En GitHub, las etiquetas son la base de los Releases.

git bisect: encontrar qué commit rompió algo

Si algo funcionaba antes y ahora no, bisect hace una búsqueda binaria en el historial: te lleva a un commit intermedio, le dices si funciona o no, y descarta la mitad de los candidatos cada vez. Con 1000 commits, lo encuentra en unos 10 pasos.

git bisect start
git bisect bad                 # el commit actual está roto
git bisect good v1.0.0         # esta versión funcionaba
# Git te lleva a un commit intermedio. Pruebas y respondes:
git bisect good                # o bien: git bisect bad
# ...repites hasta que Git indica el primer commit malo...
git bisect reset               # vuelves a tu rama

Si tienes un comando que comprueba el error (por ejemplo, tus pruebas), Git puede hacerlo solo con git bisect run npm test. Un código de salida 0 significa “bueno” y cualquier otro significa “malo”.

git worktree: dos ramas a la vez, en dos carpetas

Crea otra carpeta de trabajo conectada al mismo repositorio. Así trabajas en dos ramas a la vez sin hacer stash ni clonar de nuevo.

git worktree add ../proyecto-arreglo -b fix/urgente    # carpeta nueva con una rama nueva
git worktree list
git worktree remove ../proyecto-arreglo

También es la forma de que dos agentes de IA trabajen en paralelo sin pisarse: cada uno en su carpeta y en su rama.

Submódulos: un repositorio dentro de otro

Un submódulo incluye otro repositorio dentro del tuyo, fijado a un commit concreto. Sirve para compartir una librería propia entre proyectos.

git submodule add https://github.com/usuario/libreria.git libs/libreria
git clone --recurse-submodules https://github.com/usuario/proyecto.git
git submodule update --init --recursive

El segundo comando clona el proyecto con sus submódulos; el tercero los descarga si ya habías clonado sin ellos. Tienen su complejidad: si puedes usar un gestor de paquetes (npm, pip…), suele ser más simple.

Buscar en el código y en el historial

git grep "TODO"                      # busca texto en los archivos del repositorio
git grep -n "funcion"                # igual, mostrando el número de línea
git log -S"texto" --oneline          # commits que agregaron o quitaron ese texto
git log --grep="arreglo" --oneline   # commits cuyo mensaje contiene esa palabra
git shortlog -sn                     # cuántos commits hizo cada persona

Limpiar y mantener

git clean -n          # simulacro: muestra qué archivos sin seguimiento borraría
git clean -fd         # los borra (no se pueden recuperar)
git gc                # limpia y comprime el repositorio

Alias: atajos para tus comandos

git config --global alias.st status
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.cm "commit -m"

Después escribes git st, git lg o git cm "mensaje".

Otras herramientas que te encontrarás

  • Git LFS: Git no está pensado para archivos muy grandes (videos, modelos, bases de datos), y GitHub rechaza los de más de 100 MB. Git LFS los guarda aparte y deja en el repositorio solo una referencia.
  • Hooks: scripts que Git ejecuta en ciertos momentos, por ejemplo antes de cada commit para pasar un linter. Viven en .git/hooks; herramientas como Husky o pre-commit facilitan compartirlos con el equipo.

Actions: automatizar con CI/CD

GitHub Actions ejecuta tareas automáticas cuando pasa algo en el repositorio: un push, un pull request, una hora fija…

  • CI (integración continua): probar y revisar cada cambio automáticamente.
  • CD (entrega o despliegue continuo): publicar automáticamente cuando todo pasó correctamente.

Se configura con un archivo .yml dentro de .github/workflows/. Este ejecuta las pruebas de un proyecto Node.js en cada push a main y en cada pull request:

name: Pruebas

on:
  push:
    branches: [main]
  pull_request:

jobs:
  probar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
ClaveQué significa
nameEl nombre del flujo de trabajo (workflow).
onCuándo se ejecuta.
jobsLos trabajos que corre. Cada uno se ejecuta en una máquina limpia.
runs-onEl sistema operativo de esa máquina.
stepsLa lista de pasos de un trabajo.
usesUsa una acción ya hecha por otra persona (por ejemplo, descargar el código).
runEjecuta un comando.

Los resultados aparecen en la pestaña Actions (✔ verde o ✘ rojo) y también como checks dentro de cada pull request. Si en la protección de main activas Require status checks to pass, nadie podrá fusionar un cambio que no pase las pruebas.

Los números de versión (@v4) cambian con el tiempo: comprueba cuál es el actual en la página de cada acción.

Las claves van en Secrets, nunca en el archivo

Guárdalas en Settings → Secrets and variables → Actions y úsalas en el workflow con ${{ secrets.MI_CLAVE }}. Así no aparecen en el código ni en los registros.

Pages: publicar una web gratis

  1. Sube tu sitio al repositorio, con un index.html en la raíz (o en una carpeta docs).
  2. Ve a Settings → Pages.
  3. En Build and deployment, elige Deploy from a branch, la rama main y la carpeta / (root) (o /docs). Pulsa Save.
  4. En uno o dos minutos tu sitio estará en https://tu-usuario.github.io/nombre-del-repositorio/.

  • En el plan gratuito, Pages funciona con repositorios públicos.
  • Si tu proyecto necesita una compilación (React, Vite…), en Source elige GitHub Actions.
  • Puedes usar tu propio dominio desde la misma pantalla de configuración.

Releases: publicar versiones

Una release es una versión publicada, con notas y archivos descargables. Se apoya en una etiqueta.

  3. Elige la etiqueta, escribe un título y las notas. El botón Generate release notes las redacta a partir de los pull requests fusionados.
  4. Adjunta archivos si hace falta (instaladores, .zip…) y pulsa Publish release.

Buenas prácticas

Estos hábitos no cambian lo que Git puede hacer, pero sí cuánto te ayudará dentro de seis meses, cuando abras un proyecto viejo, o cuando otra persona lo abra por primera vez.

Mensajes de commit claros

El mensaje es lo que verás en git log cuando busques qué pasó. Escríbelo para tu yo del futuro.

  • Una línea corta (de unos 50 a 70 caracteres) que diga qué hace el commit.
  • Si hace falta, deja una línea en blanco y agrega un párrafo con el por qué.
  • Usa siempre la misma forma verbal. Un truco: debe completar la frase “Este commit… agrega el formulario”.
  • Un commit, un cambio. No mezcles una función nueva con un arreglo no relacionado.
  • Sin punto final.
EvitaMejor así
arreglosCorrige el cálculo del total con descuento
cambios variosAgrega validación al formulario de registro
listo o asdfElimina la dependencia que ya no se usa
Corrige el error (¿cuál?)Corrige el error al guardar con el nombre vacío

Para agregar un cuerpo al mensaje, usa -m dos veces: la primera es el título y la segunda, el párrafo.

git commit -m "Corrige el cálculo del total con descuento" -m "El descuento se aplicaba antes de sumar el envío, por eso el total salía menor."

Algunos equipos usan prefijos estándar (Conventional Commits) que permiten generar notas de versión automáticamente:

feat: agrega el filtro por categoría
fix: corrige el total con descuento
docs: actualiza el README
refactor: separa la lógica de validación
test: agrega pruebas del carrito
chore: actualiza dependencias

No es obligatorio. Lo importante es que todo el equipo use la misma convención.

Commits pequeños y frecuentes

  • Los commits pequeños se revisan, se deshacen y se encuentran mejor (por ejemplo, con git bisect).
  • Haz un commit cada vez que una pieza funcione. No esperes al final del día.
  • Si tu mensaje necesita una “y” (“Agrega X y corrige Y”), probablemente son dos commits.
  • Si en un mismo archivo hay cambios de dos cosas distintas, git add -p te deja elegir qué trozos entran en cada commit.

  1. Nunca escribas una clave dentro del código. Léela desde una variable de entorno (process.env.CLAVE_API en JavaScript, os.environ["CLAVE_API"] en Python).

  3. Sube un .env.example con los nombres de las variables y sin valores, para que los demás sepan qué configurar.
  4. Antes de cada commit, mira git status y git diff --staged.
  5. Activa secret scanning y push protection en el repositorio.
  6. Si usas una IA: no pegues claves en el chat, pídele que no las escriba en el código y vigila lo que sube con git add ..

URL_BASE_DE_DATOS=

git remote add origin https://github.com/tu-usuario/mi-proyecto.git
git push --force-with-lease origin main

git filter-repo quita por seguridad la conexión con origin, por eso hay que volver a agregarla. Después, avisa al equipo para que clone de nuevo el repositorio. Revisa también los registros del servicio por si alguien usó la clave.

Asume que una clave subida está comprometida

Un repositorio público lo ve todo el mundo, y los robots buscan claves a diario. Limpiar el historial no sustituye a cambiar la clave: lo primero siempre es cambiarla.

Tres listas de comprobación

Antes de…Comprueba
Hacer commitgit status y git diff --staged. ¿Solo entra lo que quieres? ¿Hay claves? ¿Funciona?
Hacer pushgit pull para traer lo nuevo, las pruebas en verde y git log --oneline -5 para ver qué vas a subir.
Abrir un pull requestRama al día con main, descripción clara y una autorrevisión: abre Files changed y léelo como si fueras otra persona.

Hábitos que te hacen ver profesional

  • main siempre funciona.
  • Una rama por tarea, y se borra al terminar.
  • Un repositorio por proyecto, con README desde el primer día.
  • Nunca git push --force sobre main.
  • No subas archivos generados ni pesados (usa .gitignore).
  • Haz push al terminar cada sesión de trabajo.
  • Con una IA: commit antes y después de cada tarea, y revisa el git diff.
