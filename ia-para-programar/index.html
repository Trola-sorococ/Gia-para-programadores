Cómo funciona y qué esperar de la IA

Las herramientas que usas para programar (ChatGPT, Copilot, Cursor, Claude y similares) se basan en modelos de lenguaje: predicen el siguiente trozo de texto a partir de lo que les das. No “entienden” tu proyecto como una persona, ni ejecutan el código en su cabeza. Predicen con mucha habilidad… y a veces se equivocan con total seguridad.

Fortalezas reales

  • Código repetitivo y boilerplate: formularios, rutas, tipos, tests básicos, configuración inicial.
  • Explicar y resumir: “¿qué hace este archivo?”, “explica este error”, “resume este diff”.
  • Traducir entre lenguajes o estilos: de un enfoque a otro, o adaptar un ejemplo a tu stack.
  • Proponer un plan: pasos, riesgos, archivos a tocar (si le pedes que piense antes de escribir).
  • Depurar con evidencia: si le pasas el mensaje de error, el traceback y lo que ya probaste, suele acertar más.

Límites que debes asumir

LímiteQué implica en la práctica
No ejecuta tu appNo “ve” que falló el login hasta que tú le pegas el error o el resultado de la prueba.
Contexto finitoSi el proyecto es grande, no tiene todo el código en mente. Tú eliges qué archivos importan.
No conoce tu negocioInventará reglas de negocio si no se las das (precios, roles, flujos reales).
Puede quedar desactualizadaAPIs, librerías y sintaxis cambian. Verifica versiones y documentación oficial.
Optimiza lo plausible, no lo correctoUn código que “se ve bien” puede estar mal o ser inseguro.

Alucinaciones: el problema #1

Una alucinación es cuando la IA afirma algo falso con tono convincente: una función que no existe, un paquete inventado, un flag de CLI que nunca hubo, o “ya está arreglado” sin haberlo comprobado.

  • Nombres de APIs o métodos que suenan reales pero no están en tu versión.
  • Dependencias o comandos que no existen (o existen con otro nombre).
  • Archivos o rutas que “deberían” estar en el repo y no están.
  • Explicaciones correctas a medias mezcladas con detalles inventados.
La confianza del tono no es una prueba

Si responde con seguridad, no significa que tenga razón. La prueba es: ¿compila?, ¿pasan las pruebas?, ¿el diff tiene sentido?, ¿existe esa API en la documentación?

Qué esperar (y qué no)

EsperableNo esperable
Acelerar el primer borradorQue entregue un sistema completo sin revisión
Ayudarte a pensar opcionesQue elija sola la arquitectura correcta para tu negocio
Señalar posibles causas de un errorQue adivine el estado de tu base de datos o tu red
Escribir tests si le das el contratoQue “garantice” que no hay bugs
Regla práctica

Trata a la IA como a un compañero rápido y junior con muy buena memoria de ejemplos: útil, productivo… y siempre con revisión humana antes de mergear.

La IA dentro de tu editor

En editores como Cursor, VS Code con Copilot, o similares, suelen coexistir tres modos. Usar el correcto ahorra tiempo y reduce desastres.

1. Chat (preguntar y diseñar)

Ventana de conversación: explicas, pegas errores, pides planes o revisiones. Ideal cuando aún no quieres tocar archivos, o cuando necesitas entender algo.

  • Diseñar un enfoque antes de editar.
  • Explicar un archivo o un error.
  • Comparar dos opciones (“A vs B, pros y contras”).
  • Pedir un checklist de revisión o un plan de pruebas.

2. Edición en línea / autocompletado

Sugiere o reescribe el trozo donde está el cursor. Sirve para cambios locales y predecibles.

  • Completar una función que ya empezaste.
  • Renombrar con coherencia en un archivo.
  • Escribir un test para una función concreta.
  • Ajustar un bloque CSS o un handler pequeño.
Acepta sugerencias cortas

Si la sugerencia en línea crece demasiado o cambia lógica de negocio, detente: mejor pásalo al chat o al agente con un prompt claro y revisa el diff.

3. Agentes (varios archivos, varios pasos)

Un agente puede leer el repo, editar varios archivos, correr comandos y seguir un plan. Es potente y también es donde más fácil es que se “desboque” si el pedido es vago.

ModoCuándo usarloRiesgo típico
ChatPensar, planear, explicar, revisarPedir código y pegarlo sin contexto del repo
Edición en líneaCambios pequeños y localesAceptar sugerencias largas sin leerlas
AgenteTareas multiarchivo bien acotadasRefactor “gratis” de media app

Flujo recomendado en el editor

  1. Define el objetivo en una frase (qué debe pasar cuando el usuario hace X).
  2. Pide un plan (sin código) y corrígelo.
  3. Ejecuta el plan por tareas pequeñas.
  4. Revisa el diff, corre pruebas y solo entonces acepta.
Permisos del agente

Si el agente puede correr terminal o instalar paquetes, supervisa esos pasos. Un npm install o un cambio de configuración puede meter dependencias que no pediste.

Escribir buenos prompts

Un buen prompt no es “hablar bonito”: es reducir ambigüedad. Cuatro piezas casi siempre mejoran el resultado: objetivo, contexto, restricciones y formato.

La receta en cuatro partes

PiezaPregunta que respondeEjemplo corto
Objetivo¿Qué debe quedar hecho?“Añadir validación de email en el registro”
Contexto¿Dónde y con qué stack?“React + Express, archivo auth.js, ya existe validatePassword”
Restricciones¿Qué no debe hacer?“No cambies la base de datos ni el diseño de la UI”
Formato¿Cómo quieres la respuesta?“Primero plan en 5 pasos; espera mi OK; luego solo el diff”

Mal vs bien

Hazme el login con IA, que quede profesional y moderno.
Objetivo: implementar login con email y contraseña.
Contexto: Node + Express, sesiones en cookie httpOnly, usuarios en Postgres.
Archivos relevantes: routes/auth.js, middleware/session.js, schema.sql.
Restricciones:
- No uses JWT.
- No instales librerías nuevas sin preguntar.
- Mantén el mismo estilo de errores (JSON { error: string }).
Formato: 1) plan breve 2) espera confirmación 3) implementa solo lo acordado.

Detalles que suelen marcar la diferencia

  • Lenguaje y versión: “Python 3.12”, “Node 20”, “React 18”.
  • Qué ya existe: “reutiliza formatDate de utils/dates.js”.
  • Qué cuenta como listo: “debe pasar npm test” o “el botón deshabilitado si el form es inválido”.
  • Tono de cambios: “cambio mínimo” vs “refactor libre” (casi siempre quieres el primero).
Una instrucción mágica (de verdad útil)

Añade: “Si falta información, pregunta antes de inventar.” Reduce alucinaciones de APIs y de reglas de negocio.

Plantilla mínima reutilizable

Contexto: [stack + archivos clave]
Objetivo: [resultado observable]
Restricciones: [qué no tocar / no instalar / no romper]
Hechos conocidos: [comportamiento actual, bugs, decisiones]
Formato de respuesta: [plan / código / checklist]
Si algo no está claro, pregunta; no inventes APIs ni archivos.

Pedir un plan antes del código

Pedir código de golpe es la forma más rápida de obtener un refactor enorme, tres librerías nuevas y un bug sutil. El plan te deja corregir la dirección barato, antes de que toque diez archivos.

Por qué planear primero

  • Detectas malentendidos (“pensaba que usabas JWT…”).
  • Acotas el alcance (“solo el endpoint, no la UI”).
  • Ordenas el trabajo en pasos verificables.
  • Evitas que el agente “mejore” cosas que no pediste.

Cómo pedirlo

Antes de escribir código, proponme un plan.
Incluye:
1) Archivos que tocarías (y por qué)
2) Pasos ordenados (cada uno verificable)
3) Riesgos o efectos colaterales
4) Qué NO harías (fuera de alcance)
5) Cómo probaríamos que quedó bien

No generes código todavía. Si falta contexto, pregunta.

Cómo corregir el plan

Responde como editor, no como espectador:

  • “Quita el paso 3: no migramos la base todavía.”
  • “Usa el patrón de errores de api/errors.js, no inventes uno nuevo.”
  • “Divide el paso 2 en dos commits: modelo y endpoint.”
  • “El paso 4 es opcional: déjalo al final y marca ‘solo si hace falta’.”
Modo plan en editores con agentes

Si tu herramienta tiene “Plan” o “Ask before apply”, úsalo para features medianas o grandes. Para un typo o un test de una línea, el plan puede ser overkill.

Señal de alarma

Si el plan es vago, el código será peor

Planes del tipo “refactorizar el módulo de usuarios y mejorar la arquitectura” casi siempre terminan en cambios difíciles de revisar. Exige archivos concretos y criterios de “listo”.

Dividir el proyecto en tareas pequeñas

La IA rinde mejor cuando cada pedido cabe en tu cabeza y en un diff revisable. “Haz toda la app” invita al caos; “añade el endpoint X y un test” suele salir bien.

De feature grande a tareas

Ejemplo: “sistema de comentarios”.

  1. Modelo / tabla comments (sin UI).
  2. Endpoint POST /posts/:id/comments con validación.
  3. Endpoint GET listado paginado.
  4. Componente de lista (solo lectura).
  5. Formulario de creación + estados de error.
  6. Pruebas de API y un smoke test de UI si aplica.

Entre cada paso: revisas, pruebas, commit. Si el paso 3 falla, no arrastras el 4–6 a medias.

Tamaño ideal de un pedido

Señal de tamaño buenoSeñal de “pide demasiado”
Puedes explicar el objetivo en 2–3 frasesNecesitas una página de requisitos
El diff cabe en una revisión de 5–15 minutosCambia 15+ archivos sin relación clara
Hay una forma clara de probarlo“Ya veremos cómo se prueba”
Una sola preocupación (API, UI o datos)Mezcla UI, migración, auth y CI a la vez

Cómo pedirle a la IA que divida

Quiero implementar: [feature].
Divide el trabajo en tareas pequeñas (máximo 30–60 minutos cada una).
Para cada tarea indica: objetivo, archivos probables, criterio de hecho y cómo probar.
Ordena por dependencias. No escribas código todavía.
Una tarea = un commit (cuando puedas)

Así, si la IA se equivoca en la tarea 4, reviertes o arreglas sin deshacer las 1–3. Combina esto con el flujo Git.

Dar contexto del proyecto

La calidad del resultado depende más del contexto que le das que de “el modelo más listo”. Sin contexto, la IA improvisa un proyecto imaginario que se parece al tuyo… hasta que rompe algo real.

Qué contexto suele importar

  • Archivos concretos: el módulo que editas, sus tests y sus vecinos inmediatos.
  • README: cómo arrancar, scripts, convenciones del repo.
  • Ejemplos de estilo: “hazlo como en services/payments.js”.
  • Errores y logs: mensaje completo, no un resumen vago.
  • Decisiones previas: “no usamos Redux”, “auth es por sesión”.

README útil para humanos y para la IA

## Stack
Node 20, Express, Postgres, React 18.

## Cómo correr
npm install
npm run dev          # API en :3000, web en :5173
npm test

## Convenciones
- Errores de API: { "error": "mensaje" }
- No usar JWT; sesiones en cookie httpOnly
- No commitear .env (usar .env.example)

Reglas del proyecto (Cursor Rules, instructions, etc.)

Muchos editores permiten reglas persistentes: preferencias que la IA debería respetar en cada chat. Guarda ahí lo estable; no copies secretos.

- Responde en español.
- Prefiere cambios mínimos y diffs revisables.
- No instales dependencias sin preguntar.
- No inventes archivos: si falta algo, dilo.
- Sigue el estilo de código existente (nombres, estructura de carpetas).
- Antes de features medianas/grandes: propone plan y espera confirmación.

Agents.md / instrucciones para agentes

Algunos flujos usan un archivo tipo Agents.md (o similar) con el mapa del repo: qué carpetas importan, comandos seguros, cómo probar. Piensa en él como un briefing para alguien nuevo en el equipo.

# Agente: guía del repo

## Mapa
- /src/api — endpoints Express
- /src/web — React (Vite)
- /tests — Jest

## Comandos seguros
- npm test
- npm run lint
- No ejecutes migraciones destructivas sin confirmación humana

## Definición de listo
- Diff acotado a la tarea
- Tests nuevos o actualizados cuando cambie comportamiento
- Sin secretos en el código
Más contexto no siempre es mejor

Pegar el repo entero satura y diluye lo importante. Mejor: pocos archivos relevantes + restricciones claras + un ejemplo del estilo deseado.

Revisar el código que genera la IA

Aceptar sin leer es la causa #1 de “la IA me rompió el proyecto”. Tu trabajo no desaparece: pasa de escribir todo a revisar y dirigir.

Checklist rápida antes de aceptar

  • ¿El cambio hace solo lo pedido (sin “mejoras” colaterales)?
  • ¿Entiendo cada archivo tocado? Si no, pide explicación del diff.
  • ¿Las APIs/importaciones existen en este repo y esta versión?
  • ¿Hay secretos, tokens o datos personales en el código?
  • ¿Maneja errores y casos borde (vacío, null, no autorizado)?
  • ¿Rompe contratos públicos (nombres, rutas, shapes JSON)?
  • ¿Hay tests o una forma manual clara de verificar?
  • ¿El estilo coincide con el proyecto (nombres, estructura, logs)?

Qué mirar en el diff

Señal sospechosaPor qué importa
Archivos no relacionados con la tareaAlcance inflado; más superficie de bugs
Dependencias nuevas sin pedirloRiesgo de supply chain y peso innecesario
Comentarios tipo “TODO: fix later”Dejó trabajo a medias o inseguro
Duplicar lógica que ya existíaNo usó el contexto del repo
Catch vacío o any por todas partesEsconde errores en lugar de tratarlos
“Compatible con todos los casos” sin testsAfirmación sin evidencia

Prompt para pedir una auto-revisión

Revisa el cambio propuesto como un code review estricto.
Lista:
1) Bugs probables
2) Cambios fuera de alcance
3) Riesgos de seguridad
4) Falta de tests
5) Alternativa más simple (si existe)
No reescribas todo: prioriza hallazgos concretos con archivo y motivo.
No merges “porque compila”

Compilar o levantar la app no prueba reglas de negocio, permisos ni regresiones. Usa el checklist y, cuando puedas, una prueba automática o un caso manual escrito.

Probar y depurar con la IA

La IA depura bien cuando le das evidencia: qué esperabas, qué pasó, cómo reproducirlo y qué ya intentaste. “No funciona” casi nunca basta.

Plantilla para reportar un error

Bug:
- Esperado: [qué debería pasar]
- Actual: [qué pasa]
- Pasos para reproducir: [1, 2, 3]
- Entorno: [OS, versión de runtime, comando]
- Evidencia: [traceback / log / screenshot textual]
- Archivos sospechosos: [rutas]
- Qué ya probé: [A, B, C]
Restricciones: cambio mínimo; no refactorices fuera del bug.
Primero hipótesis ordenadas por probabilidad; luego el fix.

Qué pegar (y qué no)

  • Sí: traceback completo, status HTTP, body de respuesta, consulta SQL fallida (sin datos sensibles).
  • Sí: el comando exacto (npm test -- auth.test.js).
  • No: contraseñas, tokens, dumps enteros de producción, datos personales de usuarios.

Pedir pruebas, no solo el arreglo

Arregla el bug descrito y añade una prueba que falle antes del fix y pase después.
Explica en 3 líneas la causa raíz.
No toques archivos fuera de: [lista].

Ciclo corto de depuración

  1. Reproduce el fallo (tú).
  2. Pide hipótesis (la IA).
  3. Elige la más probable y un experimento mínimo.
  4. Aplica el fix acotado.
  5. Vuelve a correr la misma prueba/repro.
  6. Si no queda, añade la nueva evidencia al chat (no empieces un hilo nuevo sin contexto).
Cuando la IA “arregla” inventando

Si propone una API que no existe, responde: “Esa función no está en el proyecto. Busca en el repo y usa lo existente, o di qué falta crear.”

npm test
npm run lint
git diff
git status

Aprender con la IA, no solo copiar

Si solo pegas código, aceleras hoy y te estancas mañana. La misma herramienta puede ser un tutor exigente si se lo pides.

Modos de aprendizaje útiles

ModoQué pedir
Explicar“Explícame este archivo como a alguien con 3 meses de experiencia”
Comparar“Opción A vs B: cuándo usar cada una en este repo”
Socrático“No me des la solución; hazme preguntas hasta que yo la proponga”
Ejercicios“Dame 3 ejercicios graduales sobre promesas y revisa mis respuestas”
Post-mortem“¿Qué concepto me faltó para caer en este bug?”

Prompts para entender de verdad

Explica qué hace este código, línea por bloque (no línea por línea aburrida).
Luego:
1) Analogía corta
2) 3 conceptos clave que debo dominar
3) Un ejercicio pequeño para practicar
4) Errores típicos de quien lo usa mal
Actúa como tutor. Quiero resolver X yo.
Reglas: no pegues la solución completa.
Dame pistas progresivas, una a la vez, y espera mi respuesta.
Si me atasco dos veces, muestra un esqueleto con huecos, no el código final.

Regla de oro

Si no puedes explicarlo, no lo merges aún

Antes de aceptar un cambio no trivial, pide: “explícame el diff en lenguaje simple y qué rompería si fallara”. Si la explicación no encaja con tu repo, investiga.

Seguridad y privacidad

Todo lo que pegas en un chat puede salir de tu máquina (según la herramienta y su configuración). Trata a la IA como un canal no privado por defecto.

Nunca compartas esto

  • API keys, tokens, contraseñas, cadenas de conexión con credenciales.
  • Claves privadas SSH, archivos .pem, cookies de sesión.
  • Datos personales de usuarios reales (nombres, emails, direcciones, historiales).
  • Volcados de producción con información sensible.
  • Secretos de CI (GITHUB_TOKEN con permisos amplios, etc.).
Si ya lo pegaste

Rota el secreto de inmediato (revoca y crea uno nuevo). Revisa si quedó en el historial del chat, en un commit o en un log. No “confíes” en que el proveedor lo borró.

Buenas prácticas en el día a día

PrácticaDetalle
.env fuera del repoUsa .env.example sin valores reales; ignora .env en Git.
Redacta logsAntes de pegar un error, sustituye tokens por REDACTED.
Modo privacidadSi tu herramienta ofrece “no entrenar con mis datos” o modo local/privado, actívalo en trabajo sensible.
Revisa dependencias nuevasLa IA puede sugerir paquetes poco mantenidos o con nombres parecidos a otros famosos.
Permisos mínimosNo des al agente acceso a secretos o a producción “porque es más fácil”.

Prompt seguro para pedir ayuda con auth

Necesito ayuda con autenticación.
Te paso solo el flujo y el código con secretos redactados (API_KEY=REDACTED).
No inventes claves de ejemplo que parezcan reales.
Señala riesgos OWASP relevantes (inyección, XSS, CSRF, IDOR) si aplican al cambio.
Código “seguro” generado no es auditoría

La IA puede olvidar hashing, expiración de sesiones, rate limits o autorización por recurso. Revisa auth y permisos con especial cuidado.

Flujo de trabajo con Git e IA

Git es el cinturón de seguridad cuando programas con IA: ramas, commits pequeños y revisar el diff antes de integrar. Si algo sale mal, vuelves atrás en minutos.

Flujo mínimo recomendado

  1. Crea una rama para la tarea.
  2. Pide plan → implementa un trozo pequeño.
  3. Revisa git diff (tú, no solo la IA).
  4. Prueba.
  5. Commit con mensaje claro.
  6. Repite hasta terminar; luego PR o merge a main.
git switch -c feature/validacion-email
git status
git diff
git add -p
git commit -m "feat: valida email en el registro"
git push -u origin HEAD

Por qué commits pequeños

  • El diff de un agente grande es imposible de revisar bien.
  • Puedes revertir un paso sin tirar el resto.
  • El historial explica la intención (útil para ti en dos semanas).

Checklist del diff con IA

  • ¿Hay archivos que no pediste?
  • ¿Aparecen .env, claves o binarios?
  • ¿Se reformateó medio proyecto sin necesidad?
  • ¿El mensaje de commit describe el porqué del cambio?
Si el agente se pasó de frenada

No pelees archivo por archivo a ciegas. Guarda lo bueno, descarta el resto (git restore / checkout selectivo) o vuelve al commit anterior y repite la tarea con un prompt más estricto.

git restore ruta/al/archivo
git restore .
git status

Para el flujo completo de Git y GitHub (ramas, PR, conflictos), usa la guía Git y GitHub de este mismo sitio.

Mini ritual de 2 minutos (antes de cada feature)

  1. Escribe el objetivo en una frase verificable.
  2. Lista 2–5 restricciones (“no tocar X”).
  3. Pide plan; corrige el plan.
  4. Implementa un paso; revisa diff; prueba; commit.
Si solo recuerdas una cosa

La IA multiplica tu velocidad y tus errores. El hábito que equilibra eso es: plan → trozos pequeños → revisar → probar → commit.
